# 搜索 → 记忆转化指南

## 为什么要转化

每次搜索的结果如果不记录，下次遇到同类问题时需要重新搜索。这是浪费。
把精华转化为记忆后：
- 同类问题直接查记忆，不需要再搜索
- 记忆中的最佳实践可以直接应用到代码中
- 项目积累的领域知识越多，响应越快、越准

## 什么该转化为记忆

### 必须记
- **解决方案**：明确的问题+修复方案组合，来源可靠的
- **技术选型结论**：在特定场景下推荐/不推荐某个工具，有理由的
- **架构模式**：可复用的架构设计，有适用条件和限制的
- **性能基线**：可量化的性能参考数据
- **安全规则**：OWASP 等权威来源的安全防护规则
- **行业共识**：多个权威来源一致认可的做法

### 不记
- 临时配置（适用于当前项目的特定版本号、端口号等）
- 未经验证的猜测
- 时效性极强的信息（如"当前最新版本是 X"——这种直接查）
- 纯个人观点（除非是公认的行业大牛的系统性文章）
- 与当前项目技术栈无关的知识

## 记忆文件结构

### 文件路径
```
memory/
├── MEMORY.md               # 索引文件
├── solution-{topic}.md     # 解决方案类
├── pattern-{name}.md       # 架构模式类
├── baseline-{topic}.md     # 性能基线类
├── security-{topic}.md     # 安全规则类
└── decision-{topic}.md     # 技术选型类
```

### 记忆模板（含可信度与老化追踪）

```markdown
---
name: {简洁名称，如 "Django N+1 查询优化"}
description: {一句话描述，用于未来检索，如 "Django ORM N+1 问题的标准解决方案"}
type: reference
credibility: {A/B/C}        # 信源最高等级
validity: {3m/6m/1y/2y}     # 预计有效期
last-verified: 2026-05-31   # 上次验证时间
---

## 来源
- GitHub: \[项目/Issue\](链接) — 等级: A
- Stack Overflow: \[问题标题\](链接) — 等级: B
- 搜索时间: 2026-05-31

## 问题
（1-2 句描述问题）

## 解决方案
（3-5 条要点，每条尽量标注支撑信源等级）

## 适用场景
（什么时候可以用这个知识）

## 不适用场景
（什么时候不能用——防止滥用比适用更重要）

## 注意事项
（trade-off、副作用、不适用的情况）

## 更新记录
- 2026-05-31: 初次记录
- 2026-08-31: 重新验证，结论 \[不变/已更新/已废弃\]
```

### 字段说明

| 字段 | 说明 | 填写规则 |
|------|------|---------|
| `credibility` | 信源最高等级 | A=官方文档/论文, B=高票社区, C=个人博客 |
| `validity` | 预计有效期 | AI=3m, 前端/云原生=6m, 后端=1y, 基础设施=2y |
| `last-verified` | 上次验证时间 | 记录时填写，更新时修改 |

### 老化检测与更新

每次使用记忆前，先执行老化检测：

```
读取记忆 → 查看 last-verified → 计算距今时长
  → 未超期：正常使用
  → 已超期：标注"[可能过时]" → 重新搜索验证 → 更新记忆文件
```

更新时在文件头部追加：
```markdown
> 📅 更新记录：2026-08-31 重新验证，结论 \[不变/已更新/已废弃\]
```

被证实已过时的记忆 → 移动到 `memory/archive/` 目录，文件名加 `.deprecated`。

### 索引更新

在 `MEMORY.md` 中添加一行：
```markdown
- [解决方案：Django N+1 查询优化](memory/solution-django-n-plus-one.md)
```

## 记忆使用

下次遇到相关技术问题时：
1. 先查 `MEMORY.md` 索引，看是否有相关记忆
2. 如果有 → 读取记忆文件，优先使用其中方案
3. 如果记忆中的方案不够 → 补充搜索，更新记忆

## 转化频率

- 每次搜索完成后立即判断是否有值得记忆的内容
- 不要等——搜索结束就记，防止遗忘
- 同一主题发现更好的方案 → 更新记忆，标注"2026-06-01 更新"
