# Pipeline E2E Auditor

## 核心原则

先理解系统应该做什么，再观察它实际做了什么，最后对比差异。
永远先怀疑"数据是否在传递中丢失"，再怀疑"逻辑是否写错"。
每次审计前先读 `references/` 下对应的检查清单。

## 模型选择原则

按任务类型选用模型，节省成本：

- **便宜模型** → 跑测试、等结果、看日志、收集数据、执行脚本。这类任务量大、逻辑简单，无需强推理能力。
- **贵模型 / 强模型** → 写修复方案、改代码、做根因分析、生成架构设计。这类任务需要深度推理和代码生成能力。

核心规则：能用便宜模型做的事不用贵模型，把算力花在需要"思考"的环节上。

## 三阶段审计（按顺序执行，不可跳过）

### 阶段 1：前端用户视角审计

角色：第一次使用系统的用户。

方法：
1. 启动前端开发服务器
2. 打开浏览器，遍历每个页面、按钮、输入框
3. 打开浏览器 Network 面板，截获所有 API 请求
4. 对照 `references/frontend-checklist.md` 逐项记录发现

硬性规则：
- 必须实际启动前端并用浏览器访问，禁止只读前端源码就下结论
- 只相信 Network 面板中实际收发的数据，不相信文档或注释
- 数据错误通常不抛异常——0、NaN、undefined、空列表都是信号

### 阶段 2：前后端数据传递测试

角色：数据流审计员。依赖阶段 1 截获的 API 请求。

方法：
1. 从阶段 1 截获的每个请求，提取请求体和响应体
2. 找到对应的后端接口定义（读后端源码）
3. 对照 `references/dataflow-checklist.md` 逐接口做 schema diff
4. 用 `scripts/diff_schemas.py` 自动对比关键字段

硬性规则：
- 200 OK 不代表数据正确——必须逐字段对齐
- 特别注意：字段重命名、嵌套层级变化、可选字段丢失、null vs [] 混用
- 禁止假设前后端字段名一致——必须实际对比源码

### 阶段 3：后端场景脚本审计

角色：运维脚本审计员。独立于阶段 1、2，可并行执行。

方法：
1. 找到各场景脚本入口（5 个节点的独立 py 文件）
2. 依次用 `--limit 3` 运行每个场景
3. 读取 `reports/<task_id>/` 下日志，提取所有 ERROR 和 WARNING
4. 对照 `references/backend-checklist.md` 逐项记录

硬性规则：
- 失败后禁止立即修代码——先跑完所有 5 个场景建立全局视角
- 场景失败时：找到上次成功日志，定位首次出现差异的位置
- 禁止猜测脚本逻辑——直接读脚本源码确认预期行为
- 日志中没有 ERROR 不代表成功——检查是否缺少预期的输出行

## 运行测试：启动命令与实时监控

### 启动命令模板

根据项目实际的 benchmark 场景脚本路径，生成启动命令。参考格式：

```bash
python benchmark/scene/<场景名>.py \
    --scan-model <扫描模型> \
    --fork-tree '<fork树JSON>' \
    --limit <条数>
```

**关键参数说明**：
- `--scan-model`：扫描阶段使用的模型，如 `glm-4.6`、`deepseek-v4-flash`
- `--fork-tree`：复评分叉树，JSON 格式定义初审和复核的模型链路，示例：
  ```json
  [{"first_review_model":"deepseek-v4-flash","children":[{"context_review_model":"deepseek-v4-pro"}]},
   {"first_review_model":"claude-4.5","children":[{"context_review_model":"claude-4.5"}]}]
  ```
- `--limit`：限制处理条数，首次验证建议用 `1`，稳定性测试用 `3`

### 跑测试的标准流程

**第一步：读源码确认入口**
- 搜索 `benchmark/` 或 `scene/` 目录下所有 `.py` 文件，确认场景入口路径
- 用 `grep` 搜 `argparse` 或 `--limit` 确认脚本接受哪些参数
- 确认 fork-tree 的模型名是否在项目中可用

**第二步：启动测试并实时盯日志**
- 执行命令，输出重定向到文件同时打印到终端
- 用 `tail -f` 或持续轮询日志文件，紧盯每条输出中的 `ERROR`、`WARNING`、`Traceback`、`CRITICAL`
- 记录首次出现异常的位置和上下文

**第三步：出现问题立刻修复**
- 出现 ERROR/Traceback → 立即起贵模型分析堆栈，定位根因
- 出现 WARNING → 评估严重程度，影响结果准确性的立即修复
- 脚本卡住无输出 → 检查进程状态，排查死锁或无限等待
- 输出结果异常（如全部相同分数、数据为空）→ 检查参数传递和数据源

**第四步：修复后原地重跑**
- 修复代码后，重新执行同一条命令
- 确认之前的错误已消失，新日志无异常
- 修复记录写入 audit 报告

### 禁止行为

- 禁止不读源码直接拼命令——必须先确认文件路径和参数名
- 禁止跑完看个返回码就走——必须读日志内容
- 禁止日志没 ERROR 就认为成功——检查是否缺少预期输出行

## 审计后的标准动作

1. 按严重程度排序所有发现：阻断 > 数据错误 > 显示异常 > 体验问题
2. 对每个问题定位根因，归类到：前端 / 后端 / 脚本 / 前后端对齐 / 数据
3. 生成修复计划并进入 Plan 模式，用户确认后执行
4. 修复后回到对应阶段，验证该问题已消除

## 并行策略

三个阶段可以并行启动子 agent：
- 阶段 1 和阶段 3 互不依赖，可首轮并行
- 阶段 2 依赖阶段 1 的 Network 截获数据，放第二轮
- 如果上下文充裕，三个阶段也可以串行以保证分析深度

## 脚本使用

- `scripts/run_scenario.py` — 封装单个场景启动命令，自动加 `--limit` 并收集返回码和耗时
- `scripts/diff_schemas.py` — 输入前端请求体 + 后端接口定义，输出字段级差异报告
- `scripts/parse_logs.py` — 扫描 `reports/` 目录，按 task_id 提取异常时间线

## 不做什么

- 不只看前端源码就下结论——必须启动服务用浏览器实测
- 不相信文档或注释——只相信 Network 面板中实际收发的数据
- 不假设前后端字段名一致——必须实际对比源码
- 不在遇到第一个失败时就停下来修——先跑完所有场景建立全局视角
- 不猜测脚本逻辑——直接读脚本源码确认预期行为
