# 后端场景脚本检查清单

## 运行前检查

- [ ] 确认每个场景脚本的入口文件路径和启动命令
- [ ] 确认 `--limit` 参数可用，默认用 `--limit 3` 快速验证
- [ ] 确认依赖的 DB 连接、模型服务等外部依赖可达
- [ ] 确认 `reports/` 目录可写，日志输出路径正确

## 每个场景的运行检查

5 个场景依次运行：
1. 文件过滤（file-filter）
2. 初扫（initial-scan）
3. 首次复核（first-review）
4. 上下文收集（context-collection）
5. 二次复核（second-review）

每个场景记录：
- [ ] 返回码是否为 0（非 0 立即标记为阻断）
- [ ] 实际运行时间是否在预期范围内（对比历史均值，异常慢或异常快都是信号）
- [ ] stdout 最后几行是否包含预期的成功标识（如 "done"、"finished"、"通过数"）
- [ ] 输出的评测结果数据结构是否完整（对比历史成功输出）
- [ ] `--limit 3` 的题目数是否正确输出为 3（而非 0 或全部题目）

## 日志排查

- [ ] 读取 `reports/<task_id>/` 下所有日志文件
- [ ] 提取所有 ERROR、CRITICAL、FATAL 行
- [ ] 提取所有 WARNING 行并评估严重程度
- [ ] 检查日志末尾是否有正常的结束标记（进程可能中途 crash 但没写 ERROR）
- [ ] 对比同场景上次成功的日志，定位首次差异点

## 常见后端 bug 信号

- 所有题目返回相同分数（极可能是评测逻辑写了死值）
- 运行时间异常短（可能跳过了核心处理逻辑）
- limit=3 但实际处理了 0 条或全部（参数解析问题）
- 日志中途截断无结束标记（OOM、未捕获异常、进程被 kill）
- 输出中包含 traceback 但返回码仍为 0（异常被吞但结果不可靠）

## 失败场景的定位流程

1. 读取该场景失败的完整日志
2. 读取该场景的源码，理解每个步骤的预期行为
3. 从日志定位失败发生在哪个步骤
4. 检查该步骤的输入数据是否正常（从 DB 或上游获取）
5. 检查该步骤的依赖是否可用（模型 API、文件路径）
6. 对比上次成功运行的同场景日志，找差异

## 不做什么

- 不在一个场景失败后停止——跑完所有 5 个再统一分析
- 不猜测脚本逻辑——必须读源码确认
- 不看日志中没有 ERROR 就认为成功——检查缺失的预期行
- 不跳过 limit=3 的快速验证直接跑全量——快速验证是发现结构性问题的第一关
